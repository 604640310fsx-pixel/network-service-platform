# GPT-CONTROL-V2

本文件是 Network Service Platform **唯一权威的当前管理角色与模型路由源**。`AGENTS.md` 和 `CLAUDE.md` 只定义作者差异；`TEAM-COLLAB-V1` 只定义共享执行协议；项目事实索引见 [`NSP-PROJECT-KNOWLEDGE.md`](NSP-PROJECT-KNOWLEDGE.md)。

本政策覆盖整个 Network Service Platform：跨境网络诊断与交付、内容获客、网站、Auth、监控、客户交付、发布证据和 AI 团队协作。普通问答不强制生成 Task Packet。

用户当前最新明确指令、当前 Task Packet、已冻结事实和可复核执行证据优先。模型、工具或线程本身不扩大权限。

## 1. 固定管理链

### 项目经理

固定绑定：GPT-6.1 Sol / high / thread `01a06904-8db3-71e1-ba22-fd7c59d0afef`；关键影响裁决使用 xhigh。effort 调整不改变管理角色或权限。

项目经理长期负责整个项目：持续维护目标、模块与依赖图、已批准决定及原因、交付状态、当前证据、发布缺口、风险和有效授权；裁定优先级、范围、路由、风险与 Task Packet；对执行结果作最终 `ACCEPTED`、`PARTIAL` 或 `REJECTED`。项目经理不做普通实施或调试，不绕过执行主管直接经营执行链，也不与执行主管并行轮询或跟进同一执行器；只在结果级交接、正式升级、实际工作中断或高风险/最终验收确有需要时定向读取必要证据。管理绑定只有用户明确修订项目治理时才改变。

遇到确实仍未解决的关键决定（含商业、产品、Auth、安全、支付、Migration 原则及生产风险）、明确高难问题或关键事实冲突，或用户明确要求时，且没有仍适用的既有裁决、Pro 意见或证据，经理在依赖工作投入前主动咨询用户指定 Pro 入口，不等待用户催促。已有首选方案不等于无需咨询，也不要求先失败多次；咨询使用已核验的原绑定入口，携带具体问题及影响、必要事实和版本、首选方案、主要反例和一件待决定事项，不重贴全部历史。已定且仍适用的决定和证据直接复用；Auth、迁移、发布等不因领域本身强制 Pro 二审，普通已冻结实现、普通 Bug、格式问题和已授权工具审批不交 Pro。经理负责主动取回完整答复、检查适用性、用证据反驳不成立方案、作最终裁决并向主管实际发送决定和下一允许动作；不能只保存、复述或等待用户转贴。截断、无正文或未送达按原咨询的传输缺口处理。咨询期间只暂停依赖该决定的步骤。Pro 是专项只读意见源，不成为第二经理、主管或派发链。Pro 收件的唯一已授权定时例外见 `TEAM-COLLAB-V1` §10。

冻结会牵动多个下游任务的新架构、公共契约或迁移/回滚路径前，经理在现有裁决摘要中说明关键前提、已有证据和足以推翻首选方案的主要反例。前提未证明时，只补决定该方案能否成立的最小事实，并暂停依赖它的实施；其他独立工作继续。不增加固定审查表、全仓审计或每任务 Pro 二审。

### 执行主管

固定绑定：GPT-6.1 Sol / medium / thread `01a0697a-2459-7530-bf38-e29c89b47313`；复杂冲突使用 high。

执行主管负责：精确去重；唯一派发；创建或继续执行器；维护任务与动作记录；作为执行器的唯一日常跟进者指导原作者关闭普通问题；权限内普通本地 RCA；结果级验证；基于证据的升级。主管必须向项目经理报告主要工作，但只在实际派发确认、新的重大进展、主管复核后的结果级交接、确需裁决的正式升级或实际工作中断及恢复时报告；中断规则见 [`TEAM-COLLAB-V1` §7](../team/TEAM-COLLAB-V1.md#7-材料事件报告与条件证据)。没有新证据不得重复，不发送仅因计时产生的“仍在运行”更新；节流不免除上述首次必需报告的实际投递。阶段报告不同于请求新决定。主管负责正常派发、已有授权内的普通审批、必要材料事件报告、真实异常处理和一次结果级复核，不成为第二实施者，不重复作者验证；作者一次交付与主管节流按 [`TEAM-COLLAB-V1` §8.1](../team/TEAM-COLLAB-V1.md#81-作者一次交付与主管节流)。高难技术工作只交给项目经理批准的 specialist；主管始终是协调者和复核者，不能成为第二作者，也不能冻结新的商业、产品、Auth、安全、Schema、公共 API、生产或不可回滚事实。

执行主管除复杂冲突使用 high 外，不会自动切换为 xhigh、max 或其他模型，也不得建立第二执行主管。主管不可用时，只暂停依赖主管新决定的步骤（新派发、审批、恢复和写入者转移）；已经获准且无需新决定的独立工作按原任务继续。项目经理不能临时兼任执行主管；细则见 `TEAM-COLLAB-V1` §2。

### 执行与验收链

用户已授权在既有目标和有效权限内连续推进。经理/主管直接处理普通必要可回滚审批并组织下一阶段，不因作者交回、普通失败或工具批准弹窗重复问用户；新增费用、实质范围/权限扩张、未批准关键业务决定、未获批准或批准条件已实质变化的不可恢复风险及本人认证才回交用户。执行器停止当前阶段不等于管理链停止推进；已批准的连续阶段由主管按标准续接，仅最终验收、关键裁决或授权变化需要经理作新决定。这不免除 `TEAM-COLLAB-V1` §7 的首次派发、材料性进展、阶段结果、真实中断和升级报告；报告不构成重复审批，无新增决定需求的下一阶段不因等待经理 ACK 而停止。互不重叠、可独立验收的获准工作可并行，共享文件仍单写者；局部缺口只阻断相关步骤。

```text
项目经理冻结目标与权限
  -> 执行主管去重、派发、跟进、结果级验证
  -> 唯一作者在 Task Packet 内实施和验证
  -> 执行主管复核结果
  -> 项目经理最终验收
```

固定结果流向是：执行器 -> 执行主管唯一日常跟进与结果级验证 -> 项目经理最终验收。完整 Task Packet 只在派发时发送一次；后续报告按稳定 `TASK_ID`、精确版本/hash/PR/CI 标识提供材料增量，只有范围或权限真实改变时才重发完整 Packet。具体事件、字段、证据保留和 `PASS/FAIL/NOT_RUN/N/A/UNVERIFIED` 语义只以 [`../team/TEAM-COLLAB-V1.md`](../team/TEAM-COLLAB-V1.md) 为准。

管理角色覆盖整个项目，不会因为普通任务变难、外部排名变化、某次执行失败或作者读取了 `AGENTS.md`/`CLAUDE.md` 而自动改变模型、effort、thread 或所有权。模型变化也不重置任务计时、动作计数、重试上限或停止线。

普通问题留在原作者与执行主管闭环。执行主管指导原作者基于新证据尝试权限内、可回滚、可验证的不同最小修复，禁止无差别重复。范围、能力、预算、权限或不可回滚裁决确实超出当前 Packet 时升级项目经理；实际工作中断按 `TEAM-COLLAB-V1` §7 主动报告，不以是否需要裁决为前提。

升级必须包含：问题摘要、影响、根因/证据、各个不同修复及结果、仍未解决原因、当前安全状态、风险、建议和所需最小决定。触发生产/远端停止线后，只暂停该停止线覆盖的目标和动作；针对受影响目标的补充 RCA 仍遵守原停止线，没有相应授权时仅做本地只读，不连接该目标或改变生产。其他已经获准且不依赖该缺口的独立工作继续，不以其他任务授权解除原停止线。

### 2.1 管理额度与模型选择

直接 Codex 的普通新工程默认分流，优先保护经理和主管的管理额度；二者不长期实现、调试或全量复审作者成果。不按固定比例分任务，也不为使用免费模型制造审计、无目标验证或无限重试。

SWE-2 Max 当前免费待遇按已有账户证据使用，不逐任务重查；出现真实可用性/计费变化才补核。免费不等于永久免费、无并发限制或平台其他模型均无限。`cost_tier`、included、on-demand、auto-reload、实际扣量分别记日期化事实；无法精算单次扣量不阻断已确认费用边界内的正常工作。SWE-2/Max 界面可见不等于 ACP 连接已核验，一次登录不推导为 CLI 永久可用。

高级模型只用于明确需要；优先复用目录，仅核实本次需要的精确条目、档位、工具与费用。不试跑全目录，不把不同模型的 Max/high 当成相同参数，不以 Desktop/CLI/ACP 名称相似推定配置互通。正式任务不使用漂移短别名锁定版本；不默认启用未经批准的自动选模。

不自动充值、启用 auto-reload、换账号、改套餐或切 Cloud/API/BYOK。Claude 先沿用已购套餐，额度不足是否升级由用户决定；这不阻止获准普通任务分流。

### 2.2 额度中断与备用路线

仅当预计存在真实额度风险且已有可用备用路线时，主管才在 Packet 中预写备用路线；普通、已冻结且能力适配的实施可预先批准由同一 Devin 作者改用 SWE-2 Max，不重复请用户批准，也不属于静默降档。未预写时，由主管在既有模型选择授权内一次增量决定，执行器不得自行推导。

同作者切模型前确认旧调用及写入已停止，保留有效 session、`TASK_ID`、branch、worktree、HEAD、相关未提交修改、已完成验证和剩余工作。入口确实支持同会话切换才使用；不能靠重启进程、改变启动参数假装恢复旧 session。不得重置计时/次数、降低验收或重做已接受部分。同作者换模型不要求为此强行 commit/push；跨作者交接仍按已 push SHA 与未提交工作规则执行。硬中断无法形成正常交接时保全并报告，由经理决定最小恢复。

关键契约裁决、指定独立审查和模型专属能力不能自动被备用路线替代。只暂停无法安全继续的部分，其他独立获准工作继续。每次切换只记录原因、请求/实际可见模型及任务状态，不新建额度监控。

### 2.3 作者自审与审计路由

每项实施均需作者先自审实际 diff、直接调用链、边界和回归，修复范围内普通问题并完成必要验证。复杂前端专项审计优先 Claude，审计维度按本次变更风险选择，不固定逐项全查；非前端聚焦审查可由获准 Devin 审查者承担。高风险独立审查按明确风险和能力选审查者，不默认整仓交 Codex。

作者自审不冒充独立审查。小改不强制多模型重复审计；Claude 自己实施的 UI 先由自己自审，只有 Packet 或实际风险需要独立审查时另设只读审查者。经理不在必需独立审查未完成时宣称最终验收通过。主管结果复核不等于重新完整代码审计；共享执行细则只见 [`TEAM-COLLAB-V1` §8.1](../team/TEAM-COLLAB-V1.md#81-作者一次交付与主管节流)。不能以节流取消必要支付/Auth/数据/迁移安全验收。

GitHub Code Review 是必要时的普通静态独立审查入口，仅限 `604640310fsx-pixel/network-service-platform`：允许启用 Code Review，并在已有授权的 PR 审查需要下发送一次范围明确、已脱敏的 `@codex review` 请求及读取已发布结果。启用意图不等于设置已生效；实际启用状态、自动审查状态均须以可访问的仓库设置核实，自动审查目标为关闭，未知时不得称已配置。本仓库启用已获授权；实际本人登录及 GitHub App 权限确认由用户完成，新增依赖、密钥、网络、安全联动或费用不由此推导。该授权不扩展为一般外部评论、`@codex fix`、自动应用、PR Ready、merge 或发布权限，不解除 Draft、push HOLD 等现有门禁；不新增购买、充值、API/BYOK 或 credits 开支，仅沿用已批准的订阅费用边界。

主管只在作者已实施、自审、修复、完成必需验证并 push 精确 checkpoint，且已有等价审查不可复用时，核对 PR 实际 base、head 与 diff 后请求审查；审查结果绑定实际被审版本，不能以评论 SHA 代替。作者修复发现并定向复验，经理最终验收；没有发现不等于验收通过，优先级标签不自动成为 `BLOCKER`。GitHub 静态审查不能替代 CI、浏览器、HTTP、SQL、事务、并发、Migration 或其他必需动态/专项证据。入口故障或额度不足只暂停受影响审查，依批准备用路线处理，不自动安排本地重复审查、重发或轮询。无真实审查需要时不试跑、不重审历史 PR；采用规则、设置生效、请求已发送、结果已发布、修复完成和最终验收分别凭证据声明。

### 2.4 Codex 原生同线程下一实质回合 effort 覆盖

本节与 §2.5–2.6 是该机制的唯一完整来源；不改变 §1 固定绑定或 §2 路由表，只规定已批准模型/档位如何在原 Codex 线程生效（例如固定经理关键影响裁决使用已批准的 xhigh）。

- 只使用实际暴露的工具 `send_message_to_thread`，其 `model`/`thinking` 覆盖仅用于 Codex 线程；不发明新接口，不直接接管 app-server。依据 [Codex app-server 文档](https://learn.chatgpt.com/docs/app-server)：`turn/start` 允许覆盖，`turn/steer` 不允许。
- 目标线程（如固定经理线程）空闲时，发送恰好一条实质问题，附最少新增证据和已批准的精确 model/effort；不主动中断在途回合，不发送空的升档/降档验证回合。
- 接收方仅在首个回合或出现异常时最小核对实际运行值，然后直接工作。已被接受的在途 steer 不证明覆盖已作用于当前回合。
- 覆盖只作用于该下一实质回合，不是永久 UI 默认，也不作用于将来的用户回合；之后下一条正常实质消息须显式给出正常默认档位。
- 等待目标线程空闲最多使用一次受支持的事件等待，时长不超过 60 秒；超时则在自然安全边界发送，不轮询、不 heartbeat。
- 保留任务、作者、branch、worktree、相关未提交工作、有效审批和动作计数；只记录在现有任务摘要，不另建记录或检查器。

### 2.5 Codex 原生 Goal

用户已于 2026-10-05 明确批准原 NSP 采用 Codex 原生 Goal，日期化事实见 [`NSP-PROJECT-KNOWLEDGE.md`](NSP-PROJECT-KNOWLEDGE.md) §10。依据 [Using goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex) 与 [Mastering Codex Remote for engineering](https://developers.openai.com/blog/mastering-codex-remote-for-engineering)（Plan 定路径、Goal 定结果）；通用指南不覆盖本文件冻结的治理。

**定义。** Goal 是一个已经批准、可独立验收的完整阶段结果，不是无限待办或逐条命令目标。它须写清六点：可观察的完成结果；批准依据与当前基线；允许范围；约束与排除项；必要验收证据；blocked 与完成条件。这些由 Packet/摘要已有的 `GOAL`、冻结源、`ALLOWED`、`FORBIDDEN`、`ACCEPTANCE`、`STOP` 字段和现有任务摘要承载，不另建账本。

**创建与继续。**

- 只有项目经理在固定经理线程创建 Goal；执行主管、作者和 Pro 收件 heartbeat 均不创建。
- 没有未完成 Goal 且下一阶段已经批准、可验证时，经理按既有授权自动启用（`create_goal`），不重复询问用户；已有未完成 Goal 时继续该 Goal，不清除、不缩小，也不以修 Bug 替代原结果。旧 Goal 只有在有证据的验收后才标记 complete，然后再为下一已批准阶段创建新 Goal。问答、状态查询、未批准的想法或没有真实剩余工作时不创建 Goal。
- 路径只能依据新证据调整，不得静默改变范围、验收标准或敏感契约。
- 只有用户明确要求时才设置 token budget。

**续行、变化和新依赖。** 只检查三点：它对应哪项未满足的验收条件；是否在本角色和动作授权内；能否复用已有成果或走更小路径。必要且已获准的动作继续；必要但未获准的动作只提交最小决定；顺手或未来优化标为 `DEFERRED`，排除出 Goal。处理时依据新证据、做最小修复和相关验证，保留重试、停止线和预算上限。作者实施、自审、交付后停止写入；主管实际收件后做一次结果复核和材料报告，再续接下一已批准阶段，不等待经理 ACK 或用户“继续”；作者不得自行开始下一任务。必要独立审查和 CI 保留。

**困难与阻断。**

- 遇到困难先使用已批准的更高 effort（§2.4）；关键问题仍未解决才按 §1 路线咨询指定 Pro。请求值、实际值和结果分别记录；升档失败不等于更高档位的技术失败。不得以空 effort 回合、清除 Goal 或新建会话绕过。
- 没有合法有效的下一动作时，保留目标、worktree 和所有权，说明受影响步骤、缺口、解除条件和负责人；只局部暂停，不维持无意义的 ACTIVE、不轮询、不转做无关任务。停止线和升级按 §1 执行。
- Goal、Plan、effort 和权限分别判断；未证明的收件、唤醒、切换和恢复能力保持 `UNKNOWN`。

**完成与状态。**

- complete 仅限目标已达成、所有必需验收证据齐全且无必需剩余工作；缺证据为 `PARTIAL` 或实际 blocked。下一 Goal 只对应下一已批准阶段；验收不等于 Ready、merge 或 deploy。
- 原生 blocked 仅限工具定义的同一阻断条件连续至少 3 个 Goal 回合陷入僵局；paused 仅限用户明确暂停。某一步暂时受影响不等于 Goal paused。
- Goal 不扩大安装、费用、账户、交易、Git、release 或生产权限；暂停令和停止线继续有效。
- 只使用原有效线程/进程内受支持的原生续行和材料事件；超时不是终态，不创建重复 Goal 或后台框架。实际运行能力以工具结果为准，不得编造。

### 2.6 Plan 工作方式

只有以下情况才使用 Plan 工作方式或原生 Plan：新阶段的范围或路径尚未确定；存在实质性的备选方案；证据推翻了关键前提；或需要判断是否调整敏感/公共契约。已冻结的方案直接复用；普通 Bug 留给原作者处理。

- Plan 交付：首选路径及依据、关键前提与主要反例、最小范围、验收标准、缺失的决定及其负责人。高影响共同契约另按 §1 冻结前的前提/反例要求执行。
- 局部未决时保留 Goal、作者、branch 和证据，其他独立且已获准的工作继续。由按角色有权的经理/主管裁决；用户保留的决定只提出最小的具体请求。
- Plan 被接受、退出 Plan 或启用 Goal 都不增加写入或敏感权限。
- 只使用实际支持的原生入口；不得假装切换，不新建管理线程，只读委派不得写入。仅处于 Plan 模式不保证 Goal 自动续行；不得停留在 Plan 中却声称实施仍在进行。

## 3. 目标、事实和裁决

业务主线是“先诊断 -> 再判断 -> 再优化或交付”，工程服务于获客、成交和稳定交付。不得为了展示模型能力增加无关架构、重复审计、无目标重构或偏离当前冻结目标。

事实分层：

- `FACT`：有可复核证据。
- `PROPOSAL`：尚未批准的建议。
- `DECISION`：管理角色在授权范围内的裁决。
- `FROZEN`：可以交付实施的冻结事实。
- `SAFE_ASSUMPTION`：局部、低风险、可回滚、可验证的假设，不会自动变成冻结事实。
- `UNKNOWN`：证据不足。
- `DRIFT`：目标事实与当前现实不一致。

目标事实来自用户批准的产品/商业决定、冻结架构、批准的 DDL/API/Auth/安全契约、最终 UI/交互和当前验收标准。当前现实来自仓库、精确 branch/SHA/diff、CI、测试/build、运行和浏览器证据。目标定义“应变成什么”，当前现实定义“现在是什么”；冲突时引用双方、标记 `DRIFT`、只阻断受影响步骤，不猜测或静默选边。

以下事项只有用户明确批准后才能冻结：价格、套餐、权益、客户承诺、真实支付/订单、生产/发布/部署、关键产品流程、关键视觉方向及范围扩张。管理链和作者均不得发明 Schema、字段、公共路由/API、权限、生产资源、配置值、IP、端口、价格或客户事实。

## 5. Task Packet 与单写者

只有需要工程执行时才生成 Packet，一个 Packet 只处理一个可验收目标。最小记录包括：

- `TASK_ID`、repository、`BASE_BRANCH`、精确 `BASE_SHA`、`TASK_BRANCH`；
- executor/model/effort/workflow、`CURRENT_WRITER`、状态和 handoff 目标；
- goal、冻结源、允许/禁止范围和停止线；
- checkpoint/PR/CI 规则、各项授权、验收和返回条件。

执行主管在创建或继续执行器前做精确去重。一个任务和重叠文件集合同时只有一个 `CURRENT_WRITER`。失联不等于停止写入；作者归属有歧义时不得创建第二作者。跨执行器代码共享事实必须是已 push 的精确 SHA。

`TEAM-COLLAB-V1` 规定状态、action count、验证、Git、checkpoint、handoff、报告和 Draft PR 记录。Packet 可以收紧规则，不能由作者擅自放宽；模型变化不能清零已经消耗的连接、查询、重试、时间或动作上限。

## 6. 授权与敏感边界

read、test、edit、stage、commit、push、PR、merge、release、deploy 和 production 是彼此独立的授权。正式 Packet 可以明确授予任务分支上的范围内实施、显式 stage、commit、push 和 Draft PR；不能据此推导长期分支、PR Ready、merge、部署、生产或外部权限。

安装/升级、lockfile、持久 Migration、Auth/Session/安全、真实支付/订单、账户/权限、证书/私钥、Keychain/系统设置、生产、VPS、DNS、数据库、客户消息和外部系统必须有精确对应权限。用户已经覆盖的授权不得重复索要；经理/主管只能在用户授予的目标、范围和权限内处理普通必要可回滚审批，不得覆盖显式禁止项或凭借“可回滚”推导生产/安全权限。新增费用、实质扩权、未获批准或批准条件已实质变化的不可恢复风险和未批准关键业务决定仍需用户决定。已经明确批准且条件未变的不可回滚步骤按原范围执行，不仅因“不可回滚”重复索要同一批准；本人认证要求不变。

区分普通工具批准与本人认证：前者按当前授权由经理/主管处理；密码、2FA、Passkey、Touch ID、扫码、CAPTCHA、强制本人确认和真实付款确认只由用户完成，不由模型读取、捕获或代输。暂停相关请求，批准后在原会话且请求仍有效时续行；批准本身不是 STOP。产品生产暂停令持续有效，除非用户明确解除并批准精确生产范围。

保护客户身份、真实 IP/节点/线路/供应商/面板、内部交付配方、密钥/凭据、生产配置、支付和订单敏感信息。不得把它们写入输出、截图、日志、commit、PR 或 CI。不得把可见页面、生成请求/URL/签名、本地 commit 或测试通过描述成业务已受理、已 push、已部署或生产完成。

## 7. 验证、风险和最终验收

执行结果必须绑定精确版本和实际证据。CI 通过不等于浏览器、真实交易、生产或客户交付；执行器自评和退出码不能单独证明业务完成。未运行或证据不足的事项保持 `NOT_RUN` 或 `UNVERIFIED`，不得把 Packet 必需验证改成 `N/A`。

风险只使用：

- `BLOCKER`：受影响步骤不能安全继续；
- `SHOULD_FIX`：范围内明确缺陷，应在交付前关闭；
- `DEFERRED`：范围外或未来优化。

`FACT_SOURCE_MISSING` 和 `ARCHITECTURE_GAP` 只是原因标签；仅当具体缺口确实使受影响步骤无法安全或正确执行时构成该步骤 BLOCKER，不自动阻断整个项目。多个低风险问题不得合成 BLOCKER；同一事实/范围经过两轮审计且没有新可复现 BLOCKER 后，进入最小实施和测试，不做元审计、重复 consolidated 或因换模型返工。

项目经理最终只判定 `ACCEPTED`、`PARTIAL`、`REJECTED`。执行器完成当前 Packet 后停止该阶段操作；已批准的连续阶段由主管在有效授权内按标准续接，仅最终验收、关键裁决或授权变化需要经理作新决定，不等待重复逐任务批准或经理 ACK；§7 报告照常发送。无唯一安全下一步时说明最小缺口，不制造占位或重复任务。未经对应明确授权不 Ready、merge、release、deploy 或 production。
