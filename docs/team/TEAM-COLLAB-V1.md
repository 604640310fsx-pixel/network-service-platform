# TEAM-COLLAB-V1

TEAM-COLLAB-V1 是 Network Service Platform 中 GPT、执行主管、Claude、Codex、Devin 和人工参与者共享的最小执行协议。它规定任务状态、单一写入者、验证证据、Git、checkpoint、handoff 和报告；不定义模型路由，不扩大产品、生产或 Git 权限。管理和模型路由见 [`../ai/GPT-CONTROL-V2.md`](../ai/GPT-CONTROL-V2.md)。

## 1. 任务记录与事实源

每个正式任务开始前记录并核对：

- `TASK_ID`、repository、`BASE_BRANCH`、精确 `BASE_SHA`、`TASK_BRANCH`；
- `FROZEN_SCOPE`：允许路径/行为及明确禁止项；
- `CURRENT_WRITER`：当前唯一作者；
- `STATUS`、`CHECKPOINTS`、`ACTION_COUNTS`；
- 实际验证、敏感门禁、风险/未知和一个 `NEXT_ACTION`；
- Packet 指定的 PR、CI、外部和停止规则。

授权与目标以用户最新明确决定、有效 Packet 及冻结契约为准；仓库、branch/HEAD/diff 和实际验证描述当前现实，二者不能用一条优先级互相覆盖。冲突标记 `DRIFT`，只暂停受影响步骤。GitHub 已 push 的精确 SHA 是跨执行器共享代码事实；聊天摘要、本地未提交修改和历史 Packet 不能替代它。审查必须说明实际输入版本及相关 dirty 状态；无法绑定时保持 `UNVERIFIED/STATIC_ONLY`，不拿工作区代替冻结 SHA。

规则采用版本与工程代码 `BASE_SHA` 分别记录在现有任务摘要。管理链已明确采用、可追溯的已 push 规则版本，可以来自尚未合并的任务分支；不得因当前 worktree、主线或旧项目镜像仍含旧规则就静默退回。规则版本不替代工程基线、制品或生产授权；阅读工程代码仍按当前 Packet 的精确版本进行。不为此合并规则 PR、切换工程基线、改写镜像或新建证明文件。

## 2. 状态与 CURRENT_WRITER

```text
READY -> IN_PROGRESS -> VALIDATING -> HANDOFF_READY -> DONE
任一非终态 -> BLOCKED | STOPPED
BLOCKED -> IN_PROGRESS       仅在阻塞已关闭且授权仍有效时
HANDOFF_READY -> IN_PROGRESS 接手者复核 handoff 后
```

`DONE` 和 `STOPPED` 是终态。`HANDOFF_READY` 不是最终验收；执行器不得自判 `DONE`。等待普通审批或本人认证使用现有 `BLOCKED` 并注明原因，不因出现提示就结束任务；同一会话/请求仍有效且获准后继续。终态或失效请求不得伪装恢复。作者阶段结束后由主管/经理按既有授权续接，不要求用户重复批准。

- 一个任务、一个阶段和任何重叠文件集合同时只能有一个可定位的 `CURRENT_WRITER`，例如 `CODEX:<task>`、`CLAUDE_CODE:<session>`、`DEVIN:<session>`、`HUMAN:<name>`；无人写入时用 `NONE`。
- 写入者只获得 Packet 明确授予的权限，不自动获得 commit、push、PR、merge、deploy 或 production 权限。
- 协调者可审阅和跟进，但不得与作者并行修改重叠文件。
- 失去联系不等于作者已经停止写入；所有权不明时保持 `BLOCKED`，禁止启动第二作者。
- 执行主管不可用时，只暂停依赖主管新决定的步骤：新派发、审批、恢复和写入者转移；已经获准且无需新决定的独立工作按原任务继续。项目经理不得临时兼任执行主管。项目经理可根据已送达的失败事件处理恢复裁决，不因此取得第二作者或主管的日常派发权。
- 接手前必须复核 repository、base、branch、HEAD、diff、未提交状态、最后 checkpoint 和授权，然后显式更新写入者。
- 模型、effort、workflow 或会话变化不重置任务计时、连接/查询/重试次数、`ACTION_COUNTS` 或停止线。

## 3. Action count 与 Checkpoint

`ACTION_COUNTS` 只记录 Packet 明确限额或具体风险需要的动作，如外部连接、交易、commit/push。普通读取、局部编辑和无副作用测试不逐次建立计数框架。已有明确上限不得绕过；失败、结果未知和模型切换不清零已发起动作。

Checkpoint 是证据，不是新授权；按完成的逻辑阶段记录，短任务可合并基线、验证和交接说明，不固定制造多轮检查。push 前及最终交接的必要证据不能省略，执行器不自加无业务目的的门禁。

```yaml
CHECKPOINT_ID: CP-<number>
TASK_ID: <task-id>
STATUS: <state>
CURRENT_WRITER: <writer>
BASE_SHA: <full-sha>
HEAD_SHA: <full-sha-or-WORKTREE>
CHANGED_FILES: [<paths>]
VALIDATION:
  - requirement: <Packet-or-policy-item>
    command: <actual-command-or-NONE>
    result: PASS | FAIL | NOT_RUN | N/A | UNVERIFIED
RISKS_OR_UNKNOWNS: [<item-or-NONE>]
ACTION_COUNTS: <current-counts>
NEXT_ACTION: <one-authorized-action>
```

不得复制凭据、客户数据或生产配置。失败证据不得被新 checkpoint 静默覆盖；应区分本次新增、相关既有、无关既有、环境和外部失败。

## 4. 验证规则

结果统一使用：

- `PASS`：要求已实际运行并有对应版本的成功证据；
- `FAIL`：已运行且未满足要求；
- `NOT_RUN`：没有运行；
- `N/A`：要求客观不适用，且没有被 Packet 列为必需；
- `UNVERIFIED`：缺少足够证据或证据不能绑定当前版本。

作者不得把 Packet-required validation 重标为 `N/A`。计划、命令存在、历史 run、旧 SHA、被替代 CI 或模板勾选不等于 `PASS`。

| 等级 | 最小证据 | 用途 |
| --- | --- | --- |
| `V0 STATIC` | status、范围 diff、`git diff --check`、格式/结构检查 | 所有写入任务 |
| `V1 TARGETED` | 与改动直接相关的检查或测试 | 文档、配置、单模块 |
| `V2 COMPONENT` | 受影响组件的 check/build/test | 产品模块、共享配置、CI 门禁 |
| `V3 INTEGRATION` | 跨组件、浏览器、沙箱或外部 E2E | 仅在范围和外部权限明确时 |
| `V4 PRODUCTION` | 生产验收、监控和回滚证据 | 仅限单独生产授权 |

每项证据绑定精确命令/方法、环境和 HEAD/artifact 版本。较高等级不自动授予外部、支付、设备、数据或生产权限；CI 成功不等于浏览器、真实交易、部署或流量完成。

同版本、相关环境和验收未变时复用已有证据，只补受变化影响的检查。主管定向复核具体发现与必要负测，不让 GPT/Claude 全量重复审查 Devin 或其他作者全部内容。静态推断保持 `STATIC_ONLY`；运行时结论须有对应执行证据。辅助工具两轮局部修正仍阻断目标时，交经理选择最小替代方法，不扩建验证框架；必要安全、迁移、支付和 CI 检查不跳过。

## 5. Git 与用户工作保护

权限链彼此独立：

```text
read -> test -> edit -> stage -> commit -> push -> PR -> merge -> release -> deploy -> production
```

- 所有动作限定到批准的 repository、base、task branch 和文件；stage 只用明确路径，禁止 `git add .` 和 `git add -A`。普通必要可回滚审批在用户已有授权内由经理/主管直接处理，不逐次请用户确认；上述箭头不表示后一动作自动获准。
- 不得自动 stash、reset、clean、restore、覆盖或移动用户文件，或切换含冲突修改的 worktree。主检出含用户改动时使用获准独立 worktree；worktree 隔离改动而非系统凭据、网络或进程权限，不能称为安全 sandbox。
- push 前复核 branch、remote target、base/HEAD、范围、最终 diff、敏感门禁及所有 push 前必需验证。
- 失败代码不得仅为满足 PR 模板或形成 handoff SHA 而 push。
- PR 默认 Draft，base 必须匹配 Packet。push main/长期 integration、force push、PR Ready、merge、branch 删除、release、deploy 和 production 必须分别授权。

## 6. Handoff

Handoff 的 mandatory core：

- `TASK_ID`、`STATUS`、来源/目标和 `CURRENT_WRITER`；
- 执行宿主、请求模型/effort、可见的实际值、按需的计费来源，以及实际任务链接或可验证 session ID；Devin 内使用其他提供方模型仍是 Devin 作者；同作者换模型按 `GPT-CONTROL-V2` §2.2；无链接时写 `UNAVAILABLE`，不得编造；已知请求选错须标 `ROUTE_MISMATCH`，不以 runtime UNKNOWN 掩盖；
- `BASE_BRANCH`、`BASE_SHA`、当前 branch；
- 修改文件和简要 diff；
- 实际验证及对应版本；
- 风险/未知、worktree 状态、用户修改保护；
- 一个 `NEXT_AUTHORIZED_ACTION` 和明确禁止项。

代码 handoff 必须使用已 push 的精确 `HANDOFF_SHA`/`REMOTE_SHA`，相关未提交工作为 `NONE`。设计使用批准版本；仅本地 artifact 使用批准的 Manifest、哈希和稳定位置，不伪造 Git 提交，并明确 `LOCAL_ARTIFACT` 或 `APPROVED_DESIGN`；Packet 未授权 push 时如实保持未 push。

每次 handoff 先由原作者停止写入并记录真实剩余责任，再由执行主管显式转移所有权；接手者复核全部 mandatory core 和 Packet 条件证据后才可进入 `IN_PROGRESS`。base、范围、权限、作者或 worktree 不一致时保持 `BLOCKED`，不得通过 stash/reset/clean/覆盖来接手。

## 7. 材料事件报告与条件证据

执行主管是执行器的唯一日常跟进者；项目经理不得与主管并行轮询或跟进同一作者。跟进优先响应消息事件；确需等待时使用带 cursor 的有界等待，不做短间隔 `wait`/`read_thread` 空轮询。等待超时且无新信息时不复读，不连续播报无变化等待或 ACK。正常更新限于关键进展和最终结果；实际派发/接收按下列规则确认一次，真实停工、失败或需裁决异常及时主动报告，不按“仍在运行”或计时触发；§10 的已授权 Pro 收件例外只用于取回复，不产生无变化进度广播：

- `DISPATCH_ACK`：只在实际创建任务或确认执行器收到任务后报告一次，不因等待状态重复发送；包含 `TASK_ID`、executor/model、目标与范围、base/branch、`CURRENT_WRITER`，以及执行是否已经实际开始。
- `MAJOR_PROGRESS`：只在出现材料性新证据时报告；包含当前状态、已完成的主要工作、精确新证据/版本、风险或未知和一个范围内下一动作。多阶段实施在真实实现 checkpoint 或重大验证里程碑后至少报告一次中点；不得发送 timer-only 更新。
- `RESULT_LEVEL_HANDOFF`：主管完成结果级复核后报告一次；包含可供裁决的结果、精确 SHA/artifact、实际验证、安全收尾、剩余问题和一个下一授权或动作。
- `ESCALATION`：需项目经理/用户权限或关键决定的异常应及时主动报告；包含影响、根因/证据、已尝试路径及结果、当前安全状态、建议和最小所需决定。
- `INTERRUPTION`：实际停工、执行失败、额度或平台中断、模型不可用、作者退出，以及权限或单写者卡住时，识别后向项目经理及时主动报告一次 `TASK_ID`、原因、影响、已保存状态、恢复路径和所需裁决（若无则写 `NONE`）；恢复时再报告一次。发送失败应在可记录时保留失败记录，并在下一可执行机会优先补发；平台硬中断不能保证即时发送，恢复后优先补报，项目经理可依据已送达的失败事件补位处理。状态无变化不重复报告，普通可修 Bug 不触发本事件；不得为作者监控新建定时轮询、通用调度框架或哈希框架。

节流只去掉重复和无变化消息，不免除上述首次必需报告：派发确认、材料性阶段成果、完成交接、真实中断与恢复及需裁决事项必须实际投递给指定下一负责人；正常小进展可在同一逻辑阶段合并，需处理的中断不压到最终交付。报告不构成重复审批；已批准且无需新决定的下一阶段发出必要报告后继续，不等待经理 ACK 或用户“继续”。实际投递与本地记账、处理分开：在本会话写报告、更新文件或 PR 只是内容和证据；工具接受、对方收到、开始处理和结果返回按各自证据记录，不要求每条额外人工 ACK，也不以“已发送”宣称“已处理”。发送明确失败时，由发送方保留原任务/咨询关联并处理传输缺口；发送结果未知时不盲目重复投递，优先使用原调用已有状态或受支持的恢复机制。

完整 Task Packet 首次派发一次；先确认消息未截断且关键字段齐全，截断时仅做传输补齐，不重开架构。后续引用稳定 `TASK_ID`、精确 version/hash/PR/CI ID 并只报材料增量；同一目标的范围或权限改变可以精确修订，目标变更才新建 Packet，不为每次普通修复重发全文。`DELTA_ONLY` 是报告方法，不表示旧线程上下文已被删除。没有新证据就不重复报告；禁止周期性轮询汇报、重复 readback 和反复重放完整历史。相同版本、相关环境与验收要求未变且证据仍适用时复用既有证据；仅发布制品传输、备份恢复等具体风险需要时补充相应校验，不为同一版本重复运行或生成逐文件哈希/Manifest。

按冻结目标直接完成工作，不逐条讲解工具调用；方案未变化时不重复复述需求或重写计划。不为普通任务默认增设子代理、并行审查或多轮综合报告；必要专项审查仍按具体风险和现有授权执行。精简过程说明不删减必要代码、测试及失败证据，也不以过低输出上限截断正式交接。

各事件的常用核心保持精简：

```yaml
TASK_ID: <id>
STATUS: <state>
MAJOR_WORK: <material-work-or-NONE>
RESULT_VERSION: <exact-sha-or-approved-artifact-version/hash>
ACTUAL_VALIDATIONS: [<method/result/version>]
RISKS_OR_UNKNOWNS: [<item-or-NONE>]
NEXT_ACTION: <one-authorized-action-or-NONE>
```

原始命令、日志、失败、退出码和测试证据必须保留在获准的 task、PR、CI 或 evidence 位置，不得为节省 token 而删除或隐藏；主管摘要提供可复核的精确引用。项目经理只在最终/高风险验收、正式升级或实际工作中断时读取必要证据。状态、base/branch、handoff、CI run/job ID、浏览器视口、主题、视觉偏差、迁移矩阵、外部状态、ledger、行数或其他字段只在当前 Packet、PR、具体事件或 handoff 确实要求时追加。

条件证据仍必须使用真实的 `PASS/FAIL/NOT_RUN/N/A/UNVERIFIED`；required 项没有运行就是 `NOT_RUN` 或 `UNVERIFIED`，不得写成 `N/A`，也不得用重复 boilerplate 隐藏缺失项。token/成本只使用当前可见的完整任务证据；不可见或不完整时报告 `UNKNOWN`，不得推断单次调用成本、声称零成本或另建成本监控系统。

### 7.1 协作语言、上下文分层与指令复读

- 与 Claude 协作默认使用英文，包括派发、增量指导、反馈和交接；向用户汇报使用中文。用户指定语言、产品中文文案、代码标识和原始引文保留原要求，不为统一语言翻译历史或重发已受理任务。
- 固定管理会话分三层：常驻规则保留角色、权限和必要边界；当前摘要保留在途目标、授权/暂停令、作者、分支/精确 SHA/相关未提交工作、有效会话与待处理请求关联、未关闭风险和下一动作；原始证据留在 PR、CI 或获准记录中按需读取，不逐层复制完整日志、diff、旧 Packet 或咨询全文。
- 使用当前入口实际支持的原生上下文压缩（支持时可用 `/compact`），在阶段收尾或没有待处理关键审批/关键操作的安全间隙按需压缩；不新建或迁移管理会话，不固定频繁压缩，不盲改上下文窗口或压缩阈值，不新建压缩证明文件。压缩不是额度重置，也不保证无损；压缩后按摘要续行，必要时定向补读，缺失关键事实只暂停相关动作，不重做已接受成果。
- 持续活跃工作期间，执行主管每满 1 小时、项目经理每满 3 小时，在下一安全操作间隙完整重读当前适用的全局、项目及管理协作指令；作者专属规则仅在实际适用时读。规则变化或发现执行偏差时即时读取受影响内容。仅等待或空闲时不定时读取、不唤醒、不追补次数；恢复持续工作且已超过间隔时读一次。不打断在途原子发布或本人认证；最后完整读取时间和采用版本只记在现有任务摘要，不新增计时器、轮询、检查器或证明文件。读取文件不等于其他会话已加载。

## 8. 问题闭环与升级

普通工具、脚本、测试、build、类型、参数、路径、fixture、解析器、数据接线和机械 UI 问题留在原作者/执行主管链中：读取新证据，尝试权限内、可回滚、可验证且彼此不同的最小修复，避免无差别重复。

范围、能力、预算、权限、产品/商业/Auth/安全/Schema/公共 API、生产或不可回滚问题才升级裁决；实际工作中断按 §7 报告，不以需要裁决为前提。升级必须包含：摘要、影响、根因/证据、不同修复及逐项结果、未解决原因、当前安全状态、风险、建议和最小所需决定。模型变化不允许重做相同尝试或清零停止线。

失联不等于停止。未知状态下禁止第二作者；不得自动 stash/reset/clean、删除 branch/worktree，或用 force push 失败代码制造 handoff。普通范围由原作者闭环；只有范围、能力、预算、权限或不可回滚边界确实需要裁决时才升级。

### 8.1 作者一次交付与主管节流

本节是作者闭环与主管节流的唯一主条款；`GPT-CONTROL-V2`、`AGENTS.md`、`CLAUDE.md` 只引用，不另立规则。

作者：

- 开始前先查找本任务及已验收的既有实现、预览、PR 和证据，能复用即复用，不重做；用户已确认且对同一版本、环境和验收仍适用的证据直接复用。
- 普通问题由原作者完成目标实施、自检、修复本次引入的失败和必要验证后，一次交付可用入口（URL、命令、精确 SHA/PR）及对应证据；不把可自行关闭的普通问题交回主管或用户。
- checkpoint、`ACTION_COUNTS`、模板和 handoff 等内部字段由作者/主管按现有证据自行补齐，不向用户索要。
- 缺工具、依赖、浏览器等能力，或下一步超出授权时，识别后一次说明已完成部分、精确缺口和最小所需决定；相关项保持 `NOT_RUN`/`UNVERIFIED`，不得以 HTTP 200、命令存在或推断代替功能验收，不得假 `PASS`。
- 作者自审是必需责任：针对本次实际 diff、直接调用、边界、错误处理和回归，修复普通问题后完成直接测试及必要功能/浏览器验证。作者自审不冒充独立审查；小改不强制双审。
- 冻结契约内、影响局部且直接调用清楚，没有新增公共、安全、资金或数据完整性风险、未解释异常，且必需验证完成时，作者自审后可直接交主管做一次结果级复核，无固定独立审查表或检查器。
- 作者 Packet 必需项完成后可 `HANDOFF_READY`；若独立审查被定义为下一阶段，标明待审而非最终通过，经理在必需独立审查结束前不得最终 `ACCEPTED`。
- 自审结论、必需专项审查结论和未闭环问题写入现有报告/Handoff 摘要，不另设固定字段、证明文件或检查器。

审查者：

- 复杂前端专项审计优先 Claude，其他审查按 `GPT-CONTROL-V2` 路由；审计维度按本次变更风险选择，不固定逐项全查。
- 实际跨模块/共享核心、复杂状态或恢复、反复实质修复、具体静态疑点，或验收明确要求独立审查时，按风险选一个最合适的入口：普通静态审查可用 `GPT-CONTROL-V2` §2.3 限定的 GitHub Code Review；复杂前端交互、异步状态、响应式或数据接线优先 Claude 专项。身份/所有权、CSRF、权限，资金/账本/结算、幂等、原子回滚、并发，Migration 约束和既有数据解释，或不可逆外部副作用，按实际风险安排聚焦独立安全审查，不按文件名机械触发。一个可精确限定范围且有能力的 GitHub 审查可覆盖等价安全静态审查，无须再做重复通用审查；未覆盖的必需动态/专项验证仍须完成。不同的实质风险可分别需要不同专家，不以“只审一次”掩盖缺口。
- 审查默认只读，每项发现给位置、影响、复现或静态证据和最小修复方向；原作者修复，审查者只复核修正及受影响部分。SHA 变化只重验受影响结论。

执行主管：

- 负责正常派发、已有授权内的普通工具审批、必要材料事件报告、真实异常处理和一次结果级复核（版本、范围、作者自审、必需测试/审查和未关闭风险）；不成为第二实施者，不重复作者验证，不修改作者文件。给作者完整可验收目标，不把实现、测试、修复拆成每步都要上级点头的微任务。已批准的连续阶段按标准续接，仅最终验收、关键裁决或授权变化需要经理作新决定；这不免除 §7 的首次派发、材料性进展、阶段结果、真实中断和升级报告，报告不构成重复审批，无新增决定需求的下一阶段不因等待经理 ACK 而停止。
- 作者已对同一版本给出可复核证据时，不重复运行相同测试、浏览器、主题或哈希验证；只对具体疑点、缺失证据或必要负测做定向核实。
- 一次结果级复核核对实际 base/head、范围、作者自审和必需功能/动态证据、已触发的独立审查及未关闭风险；矛盾只核对应点。缺作者验证时一次退回原作者补齐，不接手实施或启动全量重审。作者修复后定向复验；同版本且条件未变的既有审查直接复用。
- 除 §7 的一次 `DISPATCH_ACK` 外，不发送重复 ACK、“仍在等待”或无变化短轮询。
- 向会话发送前，仅确认已输入的文字才算需保护的未发送草稿；灰色建议或占位不阻断发送，不为此反复按键或重建会话。

连续推进（主管/经理）：

- 派工前先用现有任务记录、PR 和证据判断真实缺口，只做一次必要的定向版本核对（如精确 ref 的 SHA 或祖先关系）；旧 Draft PR 未合并或冲突不等于代码未进入主线。主线已有等价修复时不重派；部署事实另行核实，不由合并推导。
- 已授权阶段出结果后，主管收件、做结果级复核并续接下一授权阶段；经理在自身权限内对具体问题直接裁决，不反复向用户索要“继续”。普通工具审批出现时按现有授权及时应答，不积压。
- 状态分别报告“已发送、作者已接收并开工、已交付（精确 SHA/PR）、已验收、已部署”，不由前一状态推导后一状态。
- 每个在途目标都有明确负责人和一个下一动作；真实停工时说明原因和最小解除方式，不假称后台自动推进。
- 无剩余工作时明确报告完成；不为延续而新造任务、哈希、Manifest 或轮询。

节流不得省略 Packet 或 §4 要求的必要 CI、安全、Migration、支付检查；Claude/Devin 路由仍以 `GPT-CONTROL-V2` 为准。

## 9. 风险与停止线

只使用：

- `BLOCKER`：受影响步骤不能安全继续，并给出解除条件；
- `SHOULD_FIX`：范围内明确缺陷，应在交付前关闭；
- `DEFERRED`：范围外或未来优化。

base/repository/作者漂移、范围外必需修改、依赖或 lockfile 未授权、用户修改冲突、本人认证、Auth/安全/Migration/生产无授权、不可修复必要验证失败及 merge/deploy/删除/强制更新无授权时，暂停受影响动作。普通批准请求不是本人认证，经理/主管按现有授权应答。`FACT_SOURCE_MISSING`/`ARCHITECTURE_GAP` 仅在具体影响成立时阻断相关步骤，不扩大成全项目停工。不得用 Mock、伪造证据或第二作者绕过；当前生产暂停令不因自动续接解除。

## 10. 自动化边界

### 10.1 Devin 受管连接与审批

采用官方 CLI ACP 的受管双向连接方向，由固定主管通过实际客户端/适配启动并持有连接；不新建管理链或改迁原主管宿主。配置文本、CLI 已安装/登录和协议文档都不证明客户端/适配已经实现。入口与能力状态放在日期化任务记录，不写成永久可用。

默认采用保留权限请求、主管按授权应答的模式；具体 CLI 参数或 ACP 模式标识以已安装版本的受支持入口为准，不预设协议枚举名。主管依据当前 Packet 直接批准普通必要可回滚且已授权的操作。Desktop Smart 与 CLI/ACP 模式分别记录，不能因名称相似而视为同一配置；工具审批模式不能代替连接或扩大动作范围。Ask 用于静态阅读，Plan 用于未冻结方案；不默认使用 Bypass/Full Access。必须按实际动作、参数和副作用判断，不能把 `git *`、解释器或包管理器整类自动放行。提示词不是强制隔离，worktree 也不是 OS sandbox。

连接内的进展通知、最终 prompt 结果、错误/退出和 `session/request_permission` 分别处理，不把单次工具 completed 当整个任务完成。以协议实际返回的 session ID、工具调用及请求 ID 关联当前 TASK_ID；不猜 ID、不增建另一套任务状态机。权限请求只能依据实际动作及同一 session/工具调用已收到的更新判定，仍不足就不允许，不通过切模型或新建 session 绕过。普通审批由主管选择该请求实际提供的合规选项并应答原请求；已有授权无需再找用户。需要实质扩权、新费用、未获批准或批准条件已实质变化的不可恢复操作，或需要本人认证时，只暂停相应请求；不伪造用户输入，不默认持久化“全部允许”。

批准后在同一有效会话/请求续行，批准不是 STOP。断连、quota、进程失败或请求失效如实报告并保留现有工作；仅在当前协议和实际状态支持时恢复，不重发同目标任务，不复用过期审批。主管在 active 受管连接中收到结果不等于能后台唤醒 inactive Desktop；宿主退出/休眠或连接不存续时不得承诺即时回传。本任务不重开已终止的原 ID/跨宿主迁移实验；未来如有新的明确授权须另行界定，新接收 ID 演示也不算原主管接通。

等待最终结果期间，受管客户端应仍能接收工具更新、权限请求、错误、结束和取消事件，不在任务完成后才读取其正在等待的审批；这是运行要求，不是已实现声明，未有实际证据的接收、唤醒和恢复能力保持 `UNKNOWN`，不能声称后台仍在自动推进。持续收件不等于反复调用管理模型或定时查状态。模型询问是否继续而实施已获准时，主管在原任务给出一次明确续行，不扩大原 Ask/Plan 权限；已授权且动作可识别的工具请求在原请求上应答，并在原请求仍有效时续行，失效或终态请求不伪装恢复。超时分别看待结果等待时限、单个工具执行时限、审批请求有效期和整项任务截止，不全部设无限长，也不用短等待时限结束合法长任务。单次等待到期不证明底层动作已退出：先看原调用实际返回（是否取消子任务、有无退出证据、关联是否有效），能继续收原结果就继续收，未知既不当作已停止也不当作正常执行；不得盲目重放 push、Migration、订单或部署等可能已有副作用的动作。确需取消时使用受支持机制并确认收尾，“取消已发送”不等于进程已停止，只处理本任务拥有且获准的资源。恢复优先原任务、原作者和有效原会话，保留 branch、worktree、HEAD、相关未提交工作和有效验证；安全停止后主管仍须明确恢复责任人、解除条件和下一允许动作。客户端/适配缺陷归其经明确授权的维护作者，不自动归产品作者；没有原调用证据时不认定死锁根因，也不编写诊断或修复代码，缺安装、持久配置或特殊权限时只提交该项最小决定。

Devin 完成、失败和权限请求必须经受管连接回到主管；报告落盘、系统通知或用户截图不替代接收。日志仅作为证据。禁止以定时查询 Devin、空轮询或新增通用后台框架补这个链路。接入后仅用一次真实小任务验证版本绑定、必要审批在原请求续行、结果/失败送达和单写者收尾；对确实未覆盖的风险作最小验证，不串行安排一堆演示。

### 10.2 Pro 咨询收件的唯一定时例外

经理对咨询全程负责，发出后必须取回完整 Pro 答复、判断有效性并给主管结论，不要求用户转贴。优先实际消息返回；需要延后收件时，仅复用用户已批准的固定经理线程五分钟收件 heartbeat：存在未完成咨询才启用，取得完整答复或咨询终止后暂停；若一条咨询结束但仍有另一条已登记咨询待收件，不重复创建实例。无新答复不重读全文、不报告“仍在等”。

该例外不是 Devin 轮询许可，也不授权其他计时器、后台监控、任务派发或原主管迁移。实际运行/暂停状态必须以工具结果为准；原始问题计时不随 heartbeat 或新消息重置。若收件机制失效，只报告具体缺口，不重复创建等价自动化。

### 10.3 状态、认证与最小增量

首次实际使用新入口或有失效证据时核实一次必要能力和计费；复用已验证且仍适用的登录/模型信息，不让用户重复登录、不提取 Desktop 凭据、不重复 GitHub token 配置或克隆。未知计费不得自动调用付费路径、充值、启用 auto-reload 或切换 Cloud/API。版本、登录、套餐及 included/on-demand 读数单列日期和证据。

linkage 证据按 §7 复用；行政 thread/session ID 只用于定位，不是认证。只有真实发送、接收、审批应答和结果证据齐全时才声明对应能力已接通。必要的 ACP 适配仍须独立明确实施范围，本规则修改本身不执行安装、权限变更或任何接入代码。

### 10.4 手机协作入口

Dots 如经明确授权，仅作为用户的需求整理、转达及结果摘要入口，不取得经理、主管、作者或审批权。它只能通过实际可用且已授权的入口处理已明确绑定的原任务；不能访问时报告限制，不新建替代管理会话、同目标工程任务或私有接入。Remote 如已配对并获准，可由用户本人进入原会话；本人确认不由 Dots 代做。实际产品可用性、会话绑定、消息送达和计费来源分别记录，不从产品说明或通知推导完成；手机入口不替代 Devin 受管连接，不授权轮询、迁移、购买或扩权。详细手机助理偏好单独维护，不复制模型表；没有本机证据的能力保持 UNKNOWN。

## 11. Draft PR 作为持久任务面板

使用 [`.github/pull_request_template.md`](../../.github/pull_request_template.md) 记录 mandatory core 和 Packet 条件证据。每次获准 push/handoff 后更新实际验证、风险/未知和下一动作；PR 描述不存 secret 或生产配置。只有验收证据齐全且另获 PR Ready/merge 权限后才能退出 Draft。
